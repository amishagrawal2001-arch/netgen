⚡

DPDK tx_worker

Multi-queue per-stream sender on commodity NICs. Mellanox mlx5, Intel ice / i40e, Broadcom bnxt. Up to 16 TX cores per stream with automatic core picking based on link speed and frame size.

📊

RFC 2544 throughput

Classic IETF §26.1 binary search per frame size. 64B → 1518B across the standard IETF set. Cooperative stop, live progress polling, CSV export for customer reports.

⏱️

One-way latency

NLAT header timestamps in each UDP payload. RX-side scapy sampler computes min / avg / p50 / p99 / max over a rolling 10K-sample window. Sub-microsecond resolution on loopback.

📈

Live throughput chart

Rolling 60-second per-interface bit-rate plot, pure-QPainter (no matplotlib). Auto-scales Y from kbps to Gbps. One line per interface, color-coded legend, no extra deps.

🎯

Per-flow randomization

Spirent/Ixia-style "modifiers" — cycle src/dst IP and L4 ports across configurable ranges for 5-tuple-hash distribution. RSS and LAG balancing testing without a hardware tester.

📦

PCAP replay

Upload any capture, replay it at line rate or controlled pps. Streaming uploader handles 100+ MB captures without freezing the UI. Loop, rate-shape, or single-pass.

🕸️

Multi-device emulation

Spin up N independent routers on a single NIC. Each device gets its own VLAN subinterface plus a per-device Linux VRF, so BGP / OSPF / IS-IS sessions don't collide on TCP/179, OSPF raw sockets, or IS-IS PF_PACKET binds. Increment IPs, MACs, VLANs, and loopbacks across the batch in one click.

🛣️

Control-plane protocols

FRR 8.5 in per-device containers. BGP (IPv4 + IPv6), OSPFv2 / OSPFv3, IS-IS, and DHCPv4 / DHCPv6 — configured from the GUI, driven by the same REST API. Route-pool attachments let you advertise thousands of prefixes per neighbor without touching vtysh.

What people use it for.

Six concrete jobs Netgen does well. If your workload is here, you're a good fit.

DUT throughput characterization

Drive a router, switch, or SmartNIC up to its drop point with RFC 2544 §26.1. Get a publishable curve of max-no-drop pps vs frame size in ~14 minutes per port pair.

LAG / RSS / ECMP balance verification

Use per-flow randomization (modifiers) to cycle src/dst IPs and L4 ports across N-thousand flows. Watch which hash buckets carry which traffic on the receiving side.

Pre-prod traffic replay

Capture a slice of real traffic in production, replay it shape-preserved or rate-amplified into a staging DUT. PCAP upload handles 100 MB+ captures over slow links without freezing the UI.

End-to-end latency budgeting

NLAT timestamps in every UDP payload give you per-packet one-way latency. Trace where in a multi-hop fabric the microseconds go.

CI / regression for kernel networking

The REST API drops cleanly into Jenkins / GitHub Actions / GitLab pipelines. Tag every commit with a throughput / latency number, gate merges on regressions.

Burn-in for new hardware

Push DUTs to line rate for hours with random modifiers active. Watch for SerDes errors, memory leaks in driver code, thermal throttling under sustained load.

Control-plane scale testing

Emulate dozens of BGP / OSPF / IS-IS peers off a single server NIC — each on its own VLAN, each in its own Linux VRF so route-table state stays isolated per session. Throw them at a route-reflector or a TOR and watch convergence.

Protocol emulation, in detail.

Each emulated device is a real FRR 8.5 process tree (zebra + bgpd + ospfd + ospf6d + isisd) running in its own Docker container, pinned to its own Linux VRF on the host. Configuration drops into the container as live vtysh commands — same syntax FRR users already know.

BGP (IPv4 + IPv6)

iBGP and eBGP, dual-stack. Configure local-AS, remote-AS, neighbor IP, update-source, keepalive / hold timers. Use loopback-IP as router-id and update-source for resilient peering through ECMP. Per-neighbor selective start / stop (shut just one peer, not the whole instance). Route-pool attachments let you advertise thousands of prefixes per neighbor with one click — increment by host, subnet, or custom step. Graceful restart on by default.

OSPFv2 + OSPFv3

Both AFs as independent instances inside the same device. Configurable area-id (decimal or dotted), point-to-point network type on the interface, graceful restart toggle. Router-id auto-derived from the loopback IPv4 / IPv6. The /api/ospf/status endpoint reports per-neighbor adjacency state (Full / 2-Way / ExStart / Init / Down). Same neighbor table the GUI refresh button shows.

IS-IS (multi-level, multi-AF)

Level-1, Level-1-2, or Level-2-only via the dropdown. NET constructed from a short area-id (e.g. 49.0001 → 49.0001.0000.0000.0001.00) or supplied verbatim. IPv4 + IPv6 on the same iface, point-to-point hello interval configurable. show isis vrf <name> neighbor backs the status pane — adjacencies, hold time, system-id, area mappings.

DHCPv4 / DHCPv6

Client mode runs dhclient inside the device container, binds to its VLAN subif via PF_PACKET so VRF policy doesn't interfere with broadcast DISCOVER. Server mode runs a dnsmasq-based pool with configurable lease times, pool start / end, gateway, gateway-route push, and DHCPv6 prefix delegation. Live lease state surfaces in the GUI (lease IP, mask, gateway, expiry).

VXLAN tunnels

Up to N VXLAN tunnels per device. Each tunnel has a configurable VNI, source / destination VTEP, UDP port (default 4789), and underlay interface. Multi-tunnel batch increment on VNI, local VTEP, and remote VTEP (configurable steps: +1 / +10 / +100 / +1000 for VNI; per-octet for IPs). Tunnels show up as vx<vni>-<hash> on the host with their FDB entries visible via bridge fdb show.

Per-device isolation

Each device gets vrf-<short-id> with a unique routing table (1000–1999). Its VLAN subif moves into the VRF as kernel master, so bgpd's TCP/179 listener, ospfd's IP-89 raw socket, and isisd's PF_PACKET bind all live in that VRF's namespace. Run 10 BGP sessions on one physical NIC, all to the same peer IP space, with zero protocol-port collisions. Constraint: each device on a shared NIC needs a unique VLAN tag (server returns HTTP 409 if you try to overlap).

Under the hood: everything is real FRR — no Python mocks, no protocol stubs. docker exec ostg-frr-<id> vtysh -c 'show running-config' gives you the same output you'd see on a Cumulus or SONiC switch. The state the GUI shows is what FRR actually reports.

Installing DPDK on the Linux server

Bundled inside install_ostg_complete.py; can also be re-run standalone. Handles apt deps (build-essential meson ninja-build pkg-config libnuma-dev libelf-dev libpcap-dev libibverbs-dev libmlx5-dev rdma-core linux-headers-$(uname -r)), clones DPDK 23.11 if not present, builds with meson+ninja, builds tx_worker against the just-installed libdpdk, configures hugepages persistently (/etc/sysctl.d/99-netgen-hugepages.conf), binds NICs (vfio-pci for Intel; mlx5_core stays loaded for Mellanox), and verifies.

# DPDK only (server already installed):
sudo /opt/OSTG/resources/dpdk/install_dpdk.sh

# Non-interactive, default 1024 hugepages:
sudo AUTO_MODE=1 /opt/OSTG/resources/dpdk/install_dpdk.sh

# Watch the install log live:
ssh root@lab-box 'tail -f /var/log/netgen-install-dpdk.log'

For Intel NICs you also need IOMMU on in the bootloader — add intel_iommu=on iommu=pt to GRUB_CMDLINE_LINUX, run update-grub, reboot. The script warns but won't touch GRUB on its own. For Mellanox NICs there's nothing to do — the mlx5 PMD uses the kernel driver, so don't rebind to vfio-pci.

Server admin console — /admin.

Operators don't have to live in SSH. Every netgen-server ships with a single-page web admin portal at http://<host>:5050/admin — auth-exempt, no static assets, no template files, no separate process to deploy. Open it, see what's wrong, fix it from the browser.

1

Server health at a glance

libdpdk version, IOMMU state from /proc/cmdline, vfio module state (loadable + builtin both recognised), hugepages allocated per NUMA node, tx_worker binary presence.

System requirements.

Realistic minimums and our recommended lab spec.

Minimum (to run anything)

  • OS: Ubuntu 22.04 LTS or newer (or any DPDK 23.11-supported distro)
  • CPU: 4 cores (2 for the OS, 2 for tx_worker)
  • RAM: 4 GB (1 GB for hugepages, 1 GB for the server, 2 GB headroom)
  • NIC: Any DPDK-supported card with at least one port
  • Kernel: 5.15+ with iommu=pt intel_iommu=on (or AMD equivalent)
  • Hugepages: 512 × 2 MB minimum, 8 × 1 GB recommended

Recommended (line-rate testing)

  • OS: Ubuntu 22.04 LTS, kernel 6.x with full preempt
  • CPU: 16+ cores, all isolated from the scheduler via isolcpus=
  • RAM: 32 GB, NUMA-pinned to the NIC's socket
  • NIC: Mellanox ConnectX-6/7 or Intel E810 — 100 Gbps+ per port
  • PCIe: Gen 4 ×16 slot (Gen 3 ×16 caps at ~110 Gbps each direction)
  • Hugepages: 16 × 1 GB on the same socket as the NIC

The client (PyQt5 GUI) runs anywhere Python 3.9+ runs — Linux, macOS, Windows via WSL2. It only needs network reach to the server's port 5050. Bandwidth requirement: trivial (REST polling, few KB/s).

Frequently asked.

The questions that come up in every demo.

How do I get a license or evaluation copy?

Contact us through the GitHub issues page to discuss licensing and evaluation. Netgen is a commercial product; pricing, deployment scope, and support tiers depend on use case (single-lab, multi-site, CI integration). Request a demo and we'll work out what makes sense for your environment.

How does it compare to TRex?

TRex is older, more mature, with strong Cisco backing. Netgen has a cleaner desktop GUI, an embedded REST API any laptop can curl, and a built-in RFC 2544 wizard. Both hit line rate on the same NICs. Pick TRex for automation-first workflows on a tight budget; pick Netgen if your team wants a polished UI, embedded documentation, and a supported product with a single vendor of record.

Will it run on a VM?

Only if you can pass the NIC through (SR-IOV VF or full PCIe passthrough). DPDK needs direct hardware access — virtio / vmxnet3 won't work for line rate, though they'll work for functional testing at low pps via the scapy fallback path.

What if my NIC isn't in the support matrix?

If DPDK 23.11 supports it upstream, it'll probably work — the tx_worker code is generic rte_eth with NIC-specific branches only for mlx5/ice/i40e/bnxt feature detection. Try it, and if you hit a wall, file an issue with your dpdk-devbind --status output and we'll add a code path.

Can I run client and server on the same box?

Yes. Loopback testing is a first-class workflow — point one NIC port at another with a DAC cable, start the server on http://127.0.0.1:5050, and the client connects locally. The one-way latency sampler is most accurate in this configuration (same clock domain, no PTP needed).

Does it generate stateful TCP, or just stateless packets?

Both, in parallel. tx_worker still throws stateless packets at line rate from templates + modifiers. As of 0.2.0 there's also a real-socket stateful path: actual 3-way handshakes, per-session connection counters, kernel-reported retransmits and RTT via TCP_INFO, optional TLS termination, and an HTTP/1.1 framing mode for testing reverse proxies and WAFs. Linux hosts can pin each client onto a per-device VRF via SO_BINDTODEVICE. Drive it from the REST API (/api/stateful_tcp/*) or the new netgen-cli tcp subcommand. Stateless DPDK for line-rate forwarding tests, stateful sockets for middlebox and proxy validation — pick the right one per workload.

Can I emulate multiple routers on a single NIC?

Yes. Each "device" you add becomes a VLAN subinterface on the chosen NIC, moved into its own Linux VRF (vrf-<short-id>). The FRR container scoped to that VRF runs BGP / OSPF / IS-IS independently — TCP/179, OSPF raw sockets, and IS-IS PF_PACKET binds don't collide across devices, even on the same physical port. The Add Device dialog increments IP / MAC / VLAN / loopback across a batch so adding 8 routers is one click instead of eight. Constraint: each device on the same NIC must use a unique VLAN tag — same iface + same VLAN is rejected with HTTP 409.

How do I run it from a CI pipeline?

As of 0.2.0 there's a headless companion: netgen-cli. Installed alongside the GUI client as a standalone entry point, it wraps every common multi-device workflow — health, list, export, import, apply, status, wait — plus full tcp start-client / start-server / stats / stop for the stateful TCP surface. Auto-injects Authorization: Bearer … when NETGEN_AUTH_TOKEN is set. Drop it into Jenkins / GitHub Actions / GitLab pipelines and gate merges on the JSON it prints. The Flask REST API is still the full surface for anything netgen-cli doesn't wrap yet.

What's the latency overhead of the netgen tx path?

tx_worker → driver → wire is ~0.5 µs on Mellanox CX-7 with single-buffer mode. The NLAT timestamp is recorded after payload assembly but before the rte_eth_tx_burst, so reported latencies include the rte_eth_tx_burst overhead (~100-300 ns) plus serialization (~5 ns/B on 25G, ~1.3 ns/B on 100G).
